# Research: Link Internal Transfers

## Decisions

### Represent the pair as a separate internal-transfer record

- **Decision**: Add one workspace-scoped record that references exactly one expense and one income transaction with the same currency and amount. The rows may already exist (for synced matching) or may be created with the relationship in one paired-entry action.
- **Rationale**: Existing transactions, provider IDs, IDs, dates, categories, tags, checks, and attachments remain untouched when linked. Paired manual creation still creates two ordinary rows rather than a third transfer transaction. The relationship can be removed without rewriting either movement. It is also a direct source for reporting exclusions and suggestions can reject already-linked endpoints.
- **Alternatives considered**: Use a third transaction kind (rejected by the approved model); use a shared transfer ID copied onto both transaction rows (makes partial pair state easier to create and complicates hiding a counterpart); infer links from payment method or equal amounts (ambiguous and unsafe).

### Enforce two-sided access at the relationship boundary

- **Decision**: A user can create, change, or remove a pair only with write access to both endpoint accounts. A transfer relationship is readable only when both endpoint transactions are readable.
- **Rationale**: This follows the approved authorization/privacy rules. A linked transaction remains available under ordinary account permissions; the relationship cannot reveal the hidden counterpart.
- **Alternatives considered**: Expose the counterpart ID or label while hiding its fields (still leaks relationship details); rely only on editor visibility (does not protect direct Jazz reads/writes).

### Store policy-checkable pair facts

- **Decision**: Store the two endpoint account IDs, shared minor-unit amount, and currency on each relationship as immutable policy facts. Populate them from the current endpoint rows in the same mergeable transaction. Keep the new columns nullable only for migration compatibility; relationship policies reject rows missing them.
- **Rationale**: Jazz alpha.59 permission expressions can correlate each endpoint query to fields on the relationship row, but cannot compare two joined sibling transaction rows to each other. Storing the shared values lets policy verify each endpoint independently, reject same-account links, and preserve amount/account/currency facts during transaction edits. It also lets direct Jazz writes receive the same pair-shape checks as application workflows.
- **Alternatives considered**: Enforce pair shape only in the UI or statechart (permits malformed direct Jazz writes); add transfer metadata to each transaction (creates partial pair state and duplicates lifecycle); leave current schema and weaken direct-write guarantees (does not meet the approved authorization model).

### Keep transfer writes local-first; distinguish security from safety

- **Decision**: Link, unlink, paired creation, and linked deletion use a Jazz mergeable transaction and finish at local durability. Never wait for an exclusive transaction or global authority before allowing the offline workflow to complete. Jazz policies remain mandatory for read, insert, update, and delete authorization; transfer statecharts and domain logic own product safety decisions and report later synchronization rejection separately.
- **Rationale**: This repository installs `jazz-tools@2.0.0-alpha.59`. Its `WriteHandle.wait({ tier: 'local' })` waits for local persistence. Its `ExclusiveWriteHandle.wait()` calls `waitForExclusiveTransaction()`, which selects global durability when a server URL or native upstream is configured. Thus a configured-but-offline authority can leave an exclusive operation waiting even though local state has changed. Jazz documentation describes mergeable writes as locally committable offline and exclusive transactions as authority validated. The app's first principle is local-first.
- **Security and safety boundary**: Security means whether the identity may read, insert, update, or delete data. Keep those rules in Jazz and revalidate them at sync; UI checks are preflight feedback only. Safety means domain consistency such as compatible endpoints, reciprocal relationship facts, and a transaction having at most one effective counterpart. Put each safety rule in Jazz wherever the installed policy engine can enforce it; retain app validation for gaps and recovery. Do not categorize safety as inherently frontend-only.
- **Proven Jazz safety support**: The focused `internal-transfer-permissions.test.ts` passed against Jazz's bundled local authority. Its isolated policy fixture proves positive correlated endpoint predicates can enforce workspace, account, amount, currency, and endpoint `internalTransferId` marker facts; it mirrors the production pattern but does not instantiate the full production policy set. A second temporary probe showed Jazz accepts a positive `whereNew` guard using correlated `exists` checks against the pre-update row: allow a null new marker, allow setting a marker only when the old marker is null, or allow preserving the existing marker. The authority rejected changing one non-null marker directly to a different non-null marker. This demonstrates a Jazz-enforceable safety guard without negative `EXISTS`.
- **Required production policy improvement**: Add that marker-transition guard to transaction update policy in `src/lib/permissions.ts`. Combined with the transfer insert check that both endpoint markers equal the relationship ID, it makes reassignment of an already-linked endpoint fail at Jazz authority validation. This is stronger than frontend validation and should be the primary uniqueness defense. The temporary probe used an isolated schema, so the production policy still needs focused verification before claiming this guarantee.
- **Proven current limitation**: A temporary runtime probe tested negative correlated lookups against the installed alpha.59 local authority. Both `Not(ExistsRel(...))` and `Not(Exists(...))` were rejected when publishing permissions with `core schema policies do not support ... yet`. The policy IR and `raw(...)` can construct these expressions, but the authority cannot deploy them. The table API exposes ordinary and composite indexes, not a unique-index declaration. Therefore a direct exclusion rule saying “no other transfer may reference either endpoint” is not currently deployable through these mechanisms.
- **Unlink policy boundary and offline ordering**: A focused policy fixture tested a transfer delete rule requiring positive `exists` checks for both endpoints with null transfer markers. The authority denied direct deletion while markers remained set and denied clearing both markers plus deleting the relationship in one mergeable transaction. Clearing markers then deleting in separate transactions was accepted. In a two-replica offline probe, a delete staged on one replica and synced before marker clearing on another was rejected; syncing the marker clear later did not retry that delete, and the relationship remained. On one replica, staging clear then delete while offline and reconnecting preserved order and both writes were accepted. Therefore an offline two-write unlink is possible only with strict mutation ordering and recovery for partial completion; the current null-marker delete guard must not be added without handling that state.
- **Full-app linked deletion settlement**: The production permission suite now verifies that clearing both transaction markers in one mergeable write, then deleting the relationship and selected transaction rows together in a second mergeable write, settles at global durability under the full app policy. A minimal Jazz policy fixture confirms a transaction cannot be deleted while an explicit `s.rel` endpoint still references it, even when that fixture's transaction delete rule allows deletion; preserve the relationship and remove the transfer row in the final bundle. The original full-policy `allowDelete` expression composed two `canWriteAccount` alternatives and did not settle. Replacing it with an equivalent transfer-specific rule—owner/admin or all-account write access, or a selected-account member with write grants to both endpoint accounts—made global settlement pass. The transfer insert rule remains unchanged because this is a deletion-specific authorization expression issue, not a reason to relax link creation security.
- **Interrupted unlink recovery**: After the marker-clear write synced but before relationship deletion, the transfer row remained in authority storage. Under the current transfer read rule, the user-scoped client could no longer read it because endpoint markers were null, while the transaction rows no longer exposed the transfer ID. A disposable policy probe confirmed a positive read predicate using `anyOf([both markers match, both markers null])` makes the pending relationship visible again and allows a later delete to finish recovery. This fixture granted broad transaction reads; production must combine the pending-state predicate with `allowedTo.read` on both endpoint relations and verify that counterpart privacy remains intact.
- **Production pending-unlink read check**: `src/lib/permissions.test.ts` now exercises the actual application policy. A user who can read both endpoint accounts sees the relationship before and after both markers clear; a selected-account member with access to only one endpoint sees neither version. This validates privacy for the current positive read rule.
- **Unlink protocol for T017**: Keep unlink as two ordered mergeable writes because alpha.59 rejects clearing markers and deleting the relationship in one transaction. First read and assess both endpoints, account permissions, and the relationship. If both markers name the relationship, clear both markers atomically and await `wait({ tier: 'local' })`; only then issue a new relationship-delete mutation and await its local settlement. If both markers are already null, treat the relationship as a pending unlink and issue a fresh delete directly. Never assume Jazz retries a rejected write: if another replica's delete reaches the authority before marker clearing, that delete is rejected and is not retried when the later marker clear arrives. The durable recoverable state is then a relationship with both markers null; a later user retry must create a new delete mutation. The positive read policy allows either fully matching endpoint facts or both markers null, while retaining `allowedTo.read` checks on both endpoint relations, so a user who can read only one account cannot see the pending relationship.
- **Unlink state and interruption outcomes**: The statechart sequence is `reading -> assessing -> clearingMarkers -> trackingClearWrite -> settlingClearWrite -> deleting -> trackingDeleteWrite -> settlingDeleteWrite -> succeeded`. A pending unlink branches from assessment directly to deletion. Before marker clearing is locally durable, cancellation or shutdown may finish as `cancelled`/`closed`; after clearing is locally durable, cancellation, shutdown, delete rejection, or unknown local settlement reports `recoveryRequired` with the transfer ID and local or unresolved settlement. The issued second write is allowed to settle; stopping the actor is not treated as canceling an already issued Jazz mutation. The app tracks both Jazz transaction IDs so a later policy rejection can be reported separately from local completion. This recovery handles the verified both-null state; a one-sided marker conflict from independent offline edits remains part of T014b conflict detection and repair.
- **Verified implementation coverage**: The unlink machine tests assert local write ordering, two tracked mutation IDs, local durability, denied access, and incompatible endpoint facts. The production permission test verifies the pending relationship remains visible only to readers of both endpoint accounts. Additional interruption and multi-device convergence coverage remains part of the broader transfer review; the protocol does not claim to solve competing offline links or one-sided marker conflicts.
- **Proven offline concurrency limitation**: A temporary test used two independent Jazz contexts against the same local authority. Both read the same unlinked row, disconnected, independently set different non-null transfer markers, and staged the writes locally. After reconnecting both, both `wait({ tier: 'global' })` calls resolved. The marker-transition policy does not prevent two offline clients from assigning competing counterpart IDs; mergeable sync accepts both writes under this alpha. Keep this invariant enforced by app conflict handling and surface/repair the resulting state after sync. Revisit negative policies, unique constraints, or a future authority-serialized offline-capable primitive as Jazz evolves.
- **Local serialization**: Within one client/workspace, a domain owner must serialize safety-sensitive local mutations so two app workflows cannot both pass the same stale eligibility check. This does not claim global serialization across offline devices.
- **Late rejection**: Local completion and authority acceptance are separate outcomes. Keep a sync-rejection observer alive beyond an editor/route operation, correlate a Jazz mutation error to the originating operation where the SDK exposes that identity, and update the user if Jazz later rejects and rolls back a locally committed change. Do not make the active form wait for this outcome.
- **Alternatives considered**: Exclusive transactions provide authority serialization but violate offline completion. Mergeable transactions without a local mutation owner or post-sync conflict handling can violate the one-counterpart safety invariant. A monolithic async callback or `fromPromise` containing read/check/write/commit orchestration violates `.specify/memory/xstate.md`.

### Add separate account-level delete authority

- **Decision**: Add a distinct delete capability to account grants and an administrator-managed control before enabling linked deletion actions. Ordinary write permission alone will not authorize deleting a linked movement.
- **Rationale**: The current `accountMemberships.access` is only `read` or `write`, while the approved transfer foundation requires delete authorization to be checked separately. Current transaction deletion policy uses write access and cannot satisfy that requirement by assumption.
- **Alternatives considered**: Treat write as delete permission (contradicts the approved transfer authorization rule); make all deletions administrator-only without making the new capability assignable (does not provide the required per-account permission model).

### Filter totals from linked relationship records

- **Decision**: Workspace expense totals and categorized breakdowns exclude transactions referenced by an internal-transfer relationship. Account histories and balances retain them.
- **Rationale**: This matches the approved reporting rule while keeping the account movement visible. The legacy `transfer` payment method remains unrelated.
- **Alternatives considered**: Remove rows from all views (incorrect account balance/history); exclude by category or payment-method value (not a linked status and can hide ordinary expenses).

### Match a seven-day, exact same-currency window

- **Decision**: Suggest transactions in the active workspace with opposite kind, another account, exact currency and minor-unit amount, no current relationship, and a business date within seven calendar days before or after the edited transaction. Sort nearest dates first.
- **Rationale**: Uses the approved same-currency equality rule and the initial product default from the spec. It avoids online conversion and prioritizes likely matches.
- **Alternatives considered**: Date-only or amount-only matching (too ambiguous); cross-currency suggestions (could imply conversion); wider or user-configurable window (not requested for the first slice).

## Repository Findings

- Transactions are defined in `src/lib/schema/transactions.ts`; the app combines table schemas in `src/lib/schema.ts` and policies in `src/lib/permissions.ts`.
- Current permissions support organization roles and account grants with `read`/`write` access. Transaction deletion currently follows write access; there is no independent delete field or management control.
- Transaction editing is integrated in `TransactionEditEntry.svelte`; `TransactionForm.svelte` is presentation. The edit workflow uses `transaction-save.ts`.
- `ExpenseOverview.svelte` computes period, category, and currency totals from the transactions it receives. Account history and transaction grouping are separate and must remain unchanged.
- `src/lib/machines/independent-transaction-persistence.ts` and bank account write statecharts demonstrate resource-owning Jazz transactions and typed settlement. They are references, not a reason to reuse or relocate their orchestration.
- The current schema has migration history through `20261021T133935-3407b5b1f26c.json`; the new schema needs an additive migration from that version. No data reset is authorized.
- The installed Jazz package is alpha.59. `WriteHandle.wait({ tier: 'local' })` and `JazzClient.onMutationError()` are present in its runtime; `ExclusiveWriteHandle.wait()` waits at global durability when an authority is configured. Do not confuse local commit completion with future authority acceptance.
- The installed typed policy DSL and local authority support positive `.exists.where(...)`, correlated row references, and `.whereOld`/`.whereNew` update rules. A temporary marker-transition probe passed: the authority rejects changing a non-null transfer ID to a different one while allowing clear/relink transitions. The production policy currently checks new marker-to-relationship facts, but does not yet apply the probed old-to-new marker-transition guard; verify and add that separately as part of T014b conflict safety work.
- The local authority rejects `Not` around correlated `ExistsRel` and `Exists` when publishing policy. `Table` metadata exposes ordinary/composite indexes but no unique-index option. Do not rely on negative relationship-exclusion rules in alpha.59.
- `src/lib/permissions.ts` contains positive transfer-to-endpoint and transaction-to-transfer marker checks. The production read rule admits either a fully linked pair or a both-markers-null pending unlink, gated by read access to both endpoint transactions. The tested marker-transition guard and deterministic resolution of competing offline links remain T014b work. Separate clear-then-delete mutations are required for alpha.59; a rejected delete needs a fresh retry after the marker clear syncs.
- `src/lib/machines/transaction-edit.ts` is the form's parent machine and invokes scoped form, link, and unlink children. It currently stores `linkInput`/`unlinkInput` as pending indicators even though child state already represents operation lifecycle; prefer selectors over duplicated lifecycle flags. The integration component owns Jazz observation and parent actor lifecycle; presentation should consume a discriminated parent view model and send typed intent events.
- Installed `@xstate/svelte@5.0.0` `useActorRef` starts an actor and automatically stops it in Svelte `onDestroy`. The transaction editor currently has graceful child drain/shutdown requirements; adopting that convenience hook without preserving the shutdown protocol would stop the root prematurely.
- Cross-currency linking is deferred in this feature; the existing approved finance spec remains the future source of those requirements.
- The feature adds visible strings, so message catalog changes require `localization.md` and Paraglide compilation after implementation review.

## Risks to Resolve During Implementation

- Verify the transfer policies reject missing policy facts and malformed direct writes, including during paired creation and unlink-and-delete transactions.
- Offline cross-device writes can produce safety conflicts even though every mutation remains subject to Jazz security policies. A deterministic effective-link rule and a repair UX are required before claiming conflict handling is complete.
- Local commit may later be rejected by Jazz permissions and rolled back. The app-level observer reports that outcome separately from local completion; operation correlation is in-memory and bounded, so reloads and evicted IDs fall back to a generic notice. Local success must be phrased as locally saved.
- `Db.onMutationError()` in alpha.59 reports rejected transaction IDs and reasons and returns an unsubscribe callback. The application-readiness actor owns the observer for the active session lifetime. Link and unlink machines now register each Jazz `txId` before awaiting local durability; the root correlates matching rejections to the transfer operation and reports that rollback separately from local completion. Unlink tracks both writes. Alpha.59 exposes no acceptance event, so the in-memory correlation list is capped at 64; unmatched, evicted, and post-restart rejections receive a generic notice. This fallback preserves reporting without making local work wait for authority.
- Verify whether Jazz migration generation produces a compatible migration and snapshot from the current schema. Do not publish/reset data as part of local implementation.
- Account-level delete controls do not currently exist; keep permission grant changes in a focused review slice and inspect every affected access helper and UI caller.
