# Multiple workspaces: evidence and decisions

Inspected 2026-10-20. This is source research and proposed policy, not an implementation plan.

## Evidence boundary

The installed dependency is exactly `jazz-tools@2.0.0-alpha.59` (package.json and pnpm resolution). Findings below come from readable installed executable JavaScript, its declarations, and application source. No SDK behavior was executed and no server authorization/revocation experiment was performed. Native server internals and cache-erasure behavior have not been established by this inspection. Do not turn these limits into promises.

The [upstream repository](https://github.com/garden-co/jazz) identifies this as the v2 alpha with a different API from Classic. The [official permission documentation](https://jazz.tools/docs/auth/permissions) describes server-enforced row policies. Installed code, rather than current unversioned examples, is the version-specific reference here.

### What still needs source or runtime verification during planning

- Server behavior when a membership read policy depends on the same membership table, including removal, account grants, and profile visibility. Existing app policies are evidence of intent, not blanket proof of every new transition.
- Declared-reference compatibility of any new admission policy; the profile work in `001/plan.md` records a prior server rejection of an unsupported join.
- Atomic uniqueness and last-owner enforcement under competing clients. Do not assume ordinary local transactions serialize global decisions.
- Membership revocation propagation and cached-data visibility on disconnected devices. No claim of remote deletion, cryptographic revocation, or immediate offline erasure is justified.
- If admission ships: available trusted identity lookup/verification, secure request redemption, expiry, replay prevention, and how the first recipient membership becomes authorized. No working v2 invitation primitive was established in this inspection.

## Approved selected-account privacy boundary (D11)

The user approved account sharing that exposes the granted account and its transactions, categories/tags used on those transactions, relevant attribution, and related attachments when supported. Only minimal workspace identity is needed. Other accounts/transactions, unused catalogs, the full membership list, bank connection metadata, unrelated workspace records, and hidden-account aggregate information stay private. User-facing actions distinguish **Share account** from broader **Share workspace**.

This is a stricter target than current policies. Existing `permissions.ts` allows categories/tags and batches/templates to workspace members, and profile reads use common workspace membership rather than readable transaction attribution. These policies need review against the new boundary; hiding management screens is insufficient. New relationship-based policies require installed-SDK compilation and real-server verification after implementation approval, especially given the prior declared-reference join rejection. No feasibility claim for a particular policy expression is made here.

For writers, an explicitly authorized entry category/tag set is required. D12 is approved in principle: access levels must distinguish use of that set, creation of categories/tags, and management of the available set. Exact assignment/extension workflows and role/capability mappings are unresolved; these are capabilities, not a decision to add a named role for each. Do not infer whole-catalog access from permission to create a transaction. Privacy limits information the app provides; it cannot conceal the meaning of a category or note legitimately present on a shared transaction or erase data already downloaded.

## Review sequencing

D1 is resolved: creation and switching first, with sharing required in the full product and accounted for in the initial design. D2 is resolved: equivalent workspaces with one automatically created starting workspace. D3 is deferred at user request; continue independent decisions and revisit it before dependent navigation implementation. D4 is resolved as invitation with acceptance, with delivery/verification/lifecycle details still open. Then resolve policy decisions affecting the initial tenancy/authorization design and retain later sharing workflow decisions for their reviewed slice, update acceptance scenarios, and only then plan a focused implementation slice. No implementation task or test run is part of this research cycle.

## No read-only sharing (D13)

The user identified no product need for read-only access. Baseline account sharing includes viewing and adding/editing transactions. Catalog creation/management stays separately authorized. This does not resolve transaction deletion, account settings, or administration rights. The constitution currently requires viewer read-only behavior and the schema permits viewer roles and read grants; those artifacts must be aligned before implementation. No schema or permission changes are made by this decision record.

## Capabilities and role bundles (D14 approved)

The user selected capabilities as the authorization vocabulary. Roles are named capability bundles; future roles may combine capabilities differently, and users may receive individual scoped capability grants. Authorization must evaluate effective capabilities rather than scatter role-name checks across features. This is a target model, not a claim that the current Jazz schema or policies already implement it.

Account scope and the approved privacy boundary remain independent constraints: a capability on Checking must not expose Savings or grant unrelated workspace powers. Active membership remains required. Define capability names/scopes, initial bundles, authority to grant capabilities, and grant combination/revocation semantics before dependent implementation. Do not assume deny overrides, custom-role UI, or transitive delegation from this decision.

Current `permissions.ts` encodes role names in policy expressions. Planning must verify a schema/policy representation for capability bundles and individual grants against the installed compiler and server, including supported declared-reference joins. Align constitution and MVP role rules before changing production permissions. Roles/capability management UI remains outside the first release unless separately included.

## Multiple owners (D5 approved)

A workspace may have multiple owners. Ownership changes must preserve at least one owner, including concurrent changes. Current organization.ownerId is singular, and membership permissions do not enforce last-owner safety; planning must align both representations and the capability model. Do not infer that ordinary mergeable offline transactions guarantee this global invariant. D15 permits an owner to remove another without their approval, with clear confirmation and last-owner protection. D16 requires an existing owner’s offer and explicit recipient acceptance before ownership takes effect; pending offers do not count as owners. Exact protected capabilities and any retained lower access after removal remain open.

## Voluntary departure (D17 approved)

Collaborators can leave a workspace without owner approval. Departure ends membership-based access, including effective individual capabilities and account grants; retained grant records must not resurrect access by accident. Finance records and attribution remain. A last owner must first establish another accepted owner. No claim of immediate offline cache erasure is implied. Account-only departure, rejoining, and revocation propagation details remain for lifecycle design.

## Reversible archive (D18 approved)

After the initial create-and-switch release, an owner can archive and restore a workspace. Records remain available subject to existing access/privacy boundaries; new financial activity stops while archived. Permanent deletion is excluded. Archived read-only behavior is a workspace lifecycle restriction, not a shareable read-only access tier. Plan authoritative archive state, in-flight and offline queued write handling, invitations, and allowed administration before implementing.

## Unfinished transaction input (D8 approved in part)

On workspace switching, discard unfinished transaction input immediately, without a prompt. There is no persisted or per-workspace draft-transaction concept. Do not introduce draft recovery, switching blockers, or unsaved-input confirmation. Already-submitted writes retain their original scope and truthful settlement handling. Direct-link behavior remains undecided with D3.

## Starter-category maintenance (D9 approved in part)

The user accepts starter categories provided their values are easy to edit in one place; existing agent-created names are not considered clear or final. Current source declares default keys/kinds/system flags in ensurePersonalWorkspace (`src/lib/data.ts:28–73`), with localized labels under defaults.categories in `messages/en.json`. Planning must provide one authoritative starter definition reused by bootstrap and explicit creation, retaining localization rather than duplicating catalog definitions. Changes to optional defaults must not reseed or rewrite existing workspaces; distinguish creation defaults from required system-category repair, and preserve stable seed identities across label changes. No category renaming or implementation is authorized by this spec edit.

## Duplicate workspace names (D19 approved)

Allow duplicate names, including when creating/renaming workspaces or accepting access to an independently created same-named workspace. Identity is independent of the display name. Selection must offer privacy-safe disambiguation; no particular additional label or UI treatment is approved yet.

## Full account history (D20 approved)

Sharing grants access to the selected account’s full historical transactions and future transactions while access is active. No date-based sharing cutoff is offered. Historical supporting records follow the selected-account privacy boundary; full history does not grant access to other accounts or additional editing/administrative capabilities. Revocation still cannot promise erasure of previously downloaded records.

## Collaborative transaction editing (D21 approved)

Transaction-editing capability covers readable entries in the granted account regardless of original author. Preserve original attribution; do not replace it with the editor’s identity. Current membership, account scope, transaction validation, and archive restrictions still apply. This decision does not grant transaction deletion or cross-account moves.

## Separate transaction deletion (D22 approved)

Deletion requires its own scoped capability, available through role bundles or individual grants. Add/edit capability alone is insufficient. Current transaction delete policy delegates to canWriteAccount, so implementation must align it with the new capability model rather than merely hide a delete button. This decision does not establish hard deletion, soft deletion, undo, or retention semantics.

## Explicit onward sharing (D23 approved)

Collaborators may invite others only with a separate account-scoped sharing capability. Neither ordinary account access nor transaction/catalog powers imply invitation authority. Offered accounts and capabilities must stay within the inviter’s effective authorized scope, and recipients must accept. Self-delegation of sharing powers and ownership are not inferred; define who may delegate the sharing capability, how acceptance revalidates current authority, and what happens to pending invitations/accepted grants after inviter access changes. Data policies must enforce scope restrictions rather than trusting invitation UI.

## Sharing-delegation authority (D24 approved)

Granting invitation capability requires separate scoped delegation authority. Invitation capability alone is insufficient. Exact initial role bundles, authority to assign this delegation capability, and whether that authority can itself be delegated remain open; do not infer recursive delegation or add a new named role for each capability.

## Pending invitation invalidation (D25 approved)

Invalidate unaccepted invitations when the inviter loses authority required to grant the offered access, including membership, account scope, invitation capability, and required delegation authority. Require a new invitation from a currently authorized person, not automatic revival after authority returns. Acceptance must revalidate authority; plan concurrent acceptance/revocation handling against actual server-supported invariants. Already accepted grants are not governed by this decision.

## Accepted access independence (D26 approved)

After valid acceptance, access no longer depends on the inviter retaining membership or capabilities. Do not cascade-revoke accepted grants when the inviter leaves or loses authority. Recipient departure, explicit authorized revocation, and workspace lifecycle rules still apply. Preserve invitation provenance for attribution if needed, without using it as an ongoing authorization chain. Pending invitations remain governed by D25.

## Account-access revocation capability (D27 approved)

Revoking another person’s account access requires a separate scoped capability. Invitation and sharing-delegation capabilities do not imply revocation authority. Account-scoped revocation must not become a route to remove workspace ownership or unrelated account access. Ownership removal follows the already approved owner rules. Define effective-access sources and authority boundaries in planning so removing one grant does not falsely claim that other role-derived access disappeared.

## Online sharing and access administration (D10 approved)

Require connectivity and server acceptance for sharing and permission changes. No offline queue is offered initially. This covers invitation, ownership, membership departure/removal, and role/individual capability changes. Ordinary finance operations remain local-first; initial owner membership created with a new workspace is a separate bootstrap path. Installed WriteHandle semantics mean waiting for global acceptance does not itself prevent initial local application or queued transport. Planning must establish an actual online administration protocol rather than simply calling wait(global) and claiming no queuing. Network loss after submission needs outcome reconciliation and idempotency; it is not proof a change failed.

## Additive effective capabilities (D28 approved)

Combine applicable role-bundle capabilities and individual grants additively within their explicit scopes. No explicit deny overrides initially. A capability remains effective if any valid source still supplies it; removing one grant must not falsely promise loss of role-derived access. Membership, account scope, ownership protections, and archive restrictions remain mandatory boundaries.

## Focused creation/startup planning addendum — 2026-10-21

**Decision proposed**: Separate identity initialization, creation-only defaults, and workspace creation into machine-owned decisions plus focused I/O. Preserve current schema kind/ownerId only for compatibility; derive active access from membership and do not prefer a personal kind.

**Rationale/evidence**: `data.ts:23–156` currently combines profile lookup, owned-personal selection, membership repair, and seed replenishment. `machines/readiness.ts:205–220` separately prefers personal. Both paths need alignment; extracting defaults alone is insufficient. Optional seed replenishment conflicts with the approved rule that editing starter defaults must not rewrite existing workspaces.

**Creation/retry evidence**: Installed `dist/runtime/db.js` mergeable transaction path supports caller-supplied insert IDs, but the JavaScript insert adapter does not establish duplicate-insert idempotency. A durable attempt record plus reconciliation of actual IDs/relationships is required; stable IDs are not a reason to blindly replay inserts or upsert over renamed categories. Order bootstrap writes as organization, owner membership, then categories under current policies. A single transaction intentionally creates a complete set; inconsistent partial records become a conflict rather than automatic broad repair.

**Initialization evidence**: `dist/runtime/client.d.ts` ReadTier documentation and executable `client.js` confirm that LocalFirstUnlessEmpty may return an empty result immediately offline, unconfigured, or after connection failure. A cold empty result cannot prove first use. Proposed optional profile initialization provenance prevents accidental re-bootstrap without treating its original workspace as a selected/home workspace. Authoritative initialization knowledge is required for ambiguous cold identities; offline warm identities remain useful. Legacy missing-receipt/no-access cases require safe unavailable recovery rather than membership resurrection.

**Alternatives considered**: A Create button calling the existing bootstrap would conflate unrelated workspaces. Blind upserts risk overwriting user changes. Default selection by kind contradicts equivalent workspaces. A global serializable transaction for every local creation would unnecessarily impose authority availability, while still requiring a reviewed recovery protocol. Full capabilities/sharing implementation is beyond this first slice.

**Proposal boundaries**: Receipt schema, IndexedDB attempt journal, storage-compatible kind value, and unselected state for ambiguous startup are reviewable design choices, not prior user decisions. Full feature planning remains open where D3 or later sharing details apply. The plan script reported branch `006-multiple-workspaces` from feature resolution, but `git branch --show-current` reported actual checkout `main`; no branch was created.

## D3 resolved after creation/startup plan review

The user approved the plan and chose route-based workspace persistence. Workspace IDs in URLs determine active context independently per tab, survive reload/bookmarks/history, and do not grant authorization. Earlier deferral and interim in-memory selection proposals are superseded for final navigation. The creation data foundation remains the first implementation cycle; route mapping/layout ownership and legacy/workspace-less entry require a separate focused design before route edits. No device-local default or synchronized selection is inferred.
